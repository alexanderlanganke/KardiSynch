Enriched Follow-Up QR with Patient + Device Identity

The existing per-visit fu QR now carries patient demographics and device identity alongside clinical measurements, enabling one-scan onboarding in CardioPal.

What changed

The buildFuQrPayload function now accepts an optional patient parameter. When provided, the JSON envelope gains patient name, DOB, device type, manufacturer code, model, serial, and implant date. All new fields are additive — existing CardioPal decoders silently ignore them.

Backward compatible: Without a patient argument, the payload is identical to before. All 13 original tests still pass unchanged.

Implant date resolution

The report object carries device serial (deviceSerial) but not implant date. The implant date is resolved by matching against patient.devices[]:

const matchingDevice = patient.devices.find(
  dev => dev.serial === report.deviceSerial
      && dev.status !== 'explanted'
);
if (matchingDevice?.implant_date) d.di = matchingDevice.implant_date;

Explanted devices are excluded — only the active device's implant date is included.

What's next: CardioPal consumer side

These changes produce the enriched QR payload. CardioPal needs to consume it:

  1. Extend decodeFollowUp() in hcpQr.ts to extract fn/ln/dob/dt/dm/mn/ds/di
  2. Map compact codes back to CardioPal enums ('PM' → DeviceType.Pacemaker, etc.)
  3. Add "Scan from clinic" button in onboarding step 1
  4. Pre-fill steps 1–4 from scanned data, skip to step 5 (emergency contacts)
